# LabelKit — Project Review

## Executive summary

1. Every HIGH-severity bug in the prior tactical review (force-unwrap crash, `^FD` corruption, pipe deadlock, connect-timeout hang, template-swallow) lives in a file with **zero** test coverage — bug density and test-coverage gaps are the same files.
2. `RenderGeometry.widthDots`/`heightDots` is `Int?` (nil = continuous stock, by design — Stock.swift:16) but every consumer force-unwraps it instead of handling nil; this is one root cause manifesting at 3 independent call sites.
3. ~30 lines of print/preview/target boilerplate are duplicated near-verbatim across all 3 consumer apps (LabelCLI, ReminderList, LabelGUI) instead of living once in LabelKit.
4. `docs/` — including the only existing code-review report — is entirely untracked by git (`git status` shows `?? docs/`). It is one `git clean` away from gone.
5. Four independent hand-rolled `Error` enums, none conforming to `LocalizedError`, so every consumer app's failure output is a raw Swift enum dump.
6. The hardcoded printer IP `192.168.0.133:9100` is duplicated in 3 places with no override flag or env var.
7. Debug/observability instrumentation (OSLog + `-d` flag, added in commit `4bc80dd`) exists on exactly one subcommand of one of three executables.
8. `ResolveTemplates()!` force-unwraps a failable initializer at 2 call sites; the prior review's own recommended fix for its HIGH #6 (`init?` should actually return `nil` on failure) would turn both into new crash sites if landed alone.
9. Two renderers (`ZPL2PNGRenderer`, `LabelaryRenderer`) each reimplement dots↔inches↔mm conversion instead of reusing `Stock`'s existing helpers — exactly the duplication that let a math bug (prior review HIGH #2) ship in one renderer but not the other.
10. Test coverage (272 lines) is concentrated entirely on pure-parsing logic; `Targets.swift`, `zpl2png.swift`, `Labelary.swift`, `ZPLFormatter.swift`, `Stock.swift`, `Devices.swift` (over half the library's source) have no tests at all.

## Architectural mental model

LabelKit is a small (~1,800 LOC), single-maintainer Swift package implementing a linear pipeline: **source text → `[ZPLProcessor]` chain → `Payload` → `Target`**. `Stock` (physical media, inches) and `Device` (printer capability, dots @ DPI) are deliberately separate value types that combine into a derived `RenderGeometry`/`ZPLOptions`; this split is the core design idea and it holds up well — the DPI-tagged `Payload` that lets `Target.send(strict:)` reject mismatched-DPI output is a genuinely good safety mechanism (see "looks bad but is fine" below for why it isn't over-engineering).

Three executables consume the library — `LabelCLI` and `ReminderList` (SPM executables) and `LabelGUI` (a separate Xcode project/app) — and each reimplements its own thin "build a label, render/print it" glue rather than sharing a convenience layer, which is where most of this review's duplication findings concentrate. The library itself is cleanly layered (Labels → Processors → Previewers/Targets → Utilities) with no circular dependencies and no files over ~420 lines; architectural decay in the "god file" sense isn't present. The debt here is narrower and more concrete: an `Optional` contract (`RenderGeometry`) that's declared but never actually respected by callers, error handling that's inconsistent across the three consumer apps rather than absent, and test coverage that tracks "logic that's fun to unit test" rather than "logic that's actually risky" — the risky I/O-and-Process-shelling code (`zpl2png.swift`, `Targets.swift`) has none.

## Things that look bad but are actually fine

- **`SharedStore`'s App Group container logic** (Sources/LabelKit/Processors/StencilTemplates.swift:130-158) looks like speculative/dead over-engineering for a personal CLI tool at first glance — but `Apps/LabelGUI/LabelGUI/LabelGUI.entitlements` actually declares `group.com.peterichardson.labelkit`, and the manual-path fallback is what lets the non-sandboxed CLI examples read the same `templates.json` the sandboxed GUI writes. Intentional, not debt.
- **`assert(isContinuous == (heightInches == nil))` only running in debug builds** (Sources/LabelKit/Stock.swift:26) looks like a validation gap — but the only two construction sites today are the built-in presets (`Stock.Preset.label2x1`/`label4x`), both of which satisfy the invariant by construction. Fine as debug-only documentation for now; worth promoting to a `throws`-based guard once `Stock` becomes user-constructible from outside the package (the prior tactical review reached the same conclusion — listed there as "below cutoff").
- **Uniform `strict`/DPI check applied even to `.png` payloads** (Sources/LabelKit/Targets.swift:41-46) looks redundant since mis-targeting a PNG seems unlikely — but the type's own doc comment (Targets.swift:16-22) explains the actual scenario: the same ZPL gets rendered once and delivered to two different `Target`s (e.g. iTerm2 preview + printer), so the uniform check is deliberate design, not overreach.
- **Two rendering backends behind one `ImageRenderer` protocol** (`LabelaryRenderer` hitting a web API, `ZPL2PNGRenderer` shelling out to a bundled binary) looks like premature abstraction for a single-developer tool — but git history shows `LabelaryRenderer` came first and `ZPL2PNGRenderer` was added later specifically to remove the internet dependency (commit `a76aaf2`). The abstraction already paid for itself.
- **`Package.resolved` is gitignored** (.gitignore) — looks like a reproducibility gap, but this is the correct SwiftPM convention for a *library* package: consumers resolve against LabelKit's declared version ranges rather than a pinned lockfile, which is what an app/executable repo would instead want to commit.
